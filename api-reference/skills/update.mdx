---
title: "Update a skill"
description: "Change a skill's name, description, category, inputs, output fields, run settings, saved login, or sharing."
openapi: "PATCH /v1/skills/{slug}"
---

Send only what you want to change. You get back the skill as [Get a skill](/api-reference/skills/get) returns it, plus `changes` (what changed, in words), `warnings`, and `login`.

| Key | What it changes |
| --- | --- |
| `name`, `description` | The skill's name and description. |
| `category` | Its [category](/concepts/skills#categories), by slug. An unknown one returns `422`. A category set here is kept when categories are sorted again. |
| `inputs` | `add` new inputs, `update` existing ones (`rename`, `type`, `default`, `required`, `description`), or `remove` some. See [Inputs](#inputs). |
| `outputs` | `update` output fields (`rename`, `description`, `type`) or `remove` them. See [Output field types](#output-field-types). |
| `default_max_results` | Rows a run returns when the caller does not say. `0` means all. |
| `browser_type`, `proxy_config`, `profile_id`, `scrape_mode` | How it runs by default. See [Run settings](/guides/run-a-skill#run-settings). |
| `data_retention_days` | How long run rows are kept, 1–90. |
| `login_id` | The [saved login](/concepts/logins-and-browser-profiles#saved-logins) it signs in with. `null` or `""` removes it. Needs `logins:write`. |
| `visibility`, `workspace_id` | `private` (only you) or `workspace` (shared with a team workspace; name it with `workspace_id` if you are in several). |

**Inputs and output fields.** Renaming one renames it in the skill's steps too. A change to the steps becomes a new [version](/concepts/keeping-skills-working#versions).

To **add** output fields, use [Improve a skill](/api-reference/improvements/improve) with `mode: "add_fields"`: the skill has to learn where they are.

**Who.** The owner or a workspace editor. `login_id` and `visibility` are owner only, and a login is only used on the owner's own runs. Needs `skills:write`.

MCP tool: `update_skill`.

## Inputs

How inputs act (`request`, `filter`, `step`) is explained in [Inputs](/concepts/skills#inputs). Each entry in `inputs.add` takes:

| Key | What it is |
| --- | --- |
| `name` | The input's name: letters, digits, and `_`, up to 64 characters, not starting with a digit. |
| `type` | `string` (default), `number`, `integer`, or `boolean`. |
| `description`, `default` | Optional. |
| `required` | Defaults to `true` for a `step` input and `false` for a `request` input or a `filter`. When a run gives one of those no value, it runs as it did before the input existed. |
| `acts_as` | `request`, `filter`, or `step`. Optional: `where` says it. |
| `where` | Where a `request` input goes, what a `filter` reads, or the value a `step` input replaces. See below. |
| `recorded_value` | For a `step` input: the value the recording typed or opened. It must appear in the steps. |
| `known_values` | Values the site is known to take. They become the input's `examples` in `input_schema`. |

`where` for each way:

| Acts as | `where` |
| --- | --- |
| `request`, query parameter | `{"in": "query", "key": "q"}`. A key the call already sends keeps its value when the input is left out. |
| `request`, address path | `{"in": "path", "template": "https://example.com/categories/{value}.rss"}`. A full `https` address on the same host as the skill's API, with `{value}` once and no query. Left out, the skill reads its usual address. |
| `request`, request body | `{"in": "body", "key": "/filters/category"}`, a JSON pointer into the call's JSON body. |
| `filter` | `{"kind": "contains", "fields": ["title", "department"]}`. `kind` is `contains`, `equals`, `one_of`, `min`, `max`, or `since`. On a skill built on an open API, `paths` (JSON pointers inside each record, such as `/departments/0/name`) can read values the rows do not return. Send `fields` or `paths`, not both. |
| `step` | `{"recorded_value": "Austin"}`, the same as `recorded_value`. |

To turn on an entry from the skill's [`available_inputs`](/api-reference/skills/get#available-inputs), send it as it is. Its extra keys (`example`, `verified`, `check`, `on`) are ignored.

```bash
curl -X PATCH https://api.valendata.com/v1/skills/greenhouse-jobs \
  -H "Authorization: Bearer $VALENDATA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "inputs": {
      "add": [
        {"name": "department", "acts_as": "filter", "where": {"kind": "contains", "fields": ["department"]}},
        {"name": "posted_since", "acts_as": "filter", "where": {"kind": "since", "fields": ["posted_at"]}}
      ]
    }
  }'
```

Without `acts_as` and `where`, an input on a skill built on an open API is mapped from its name: a query parameter the call already sends, `min_<field>` or `<field>_min` as `min` on that field (`max_` and `_since` the same way), a field's own name as `contains` on it, and `keyword`, `search`, or `q` as `contains` on every field. Any other name returns `422` asking how it acts. On a skill built from a recording, an input without `recorded_value` or `where` is added but changes nothing yet.

These return `422` with the reason: a `step` input on a skill built on an open API (it has no steps), a `request` input on a skill with no API call (use a `filter`), a filter field the skill does not return, and a path template on another host.

To turn an input off, send its name in `inputs.remove`. A `request` input or a `filter` always comes off, and the API call goes back to what it sent before. A `step` input the steps still use returns `422` naming the step.

## Output field types

`outputs.update[].type` is one of `string`, `number`, `integer`, `boolean`, `date`, `datetime`, `url`, `price`, `chance`, `percent`, `count`, `duration`, `array`, or `object`. What each one returns is in [Output field types](/concepts/skills#output-field-types). `string` makes a field text again.

```json
{"outputs": {"update": [{"name": "yes_price", "type": "chance"}, {"name": "end_date", "type": "datetime"}]}}
```

The new type applies from the next run. Values that do not fit are kept as printed and listed in the run's `type_notes`.
