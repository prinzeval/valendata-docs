title: "Keeping skills working"
description: "Websites change. Valendata versions every skill, works out why a run failed, repairs only what can be repaired, proves each repair, and takes a faster route when one is safe."
---

A skill saves the steps to take on a website and how to read the results. Websites change their layout, and steps that worked yesterday can break today. Valendata is built so that a skill either keeps returning correct rows or tells you clearly why it cannot. It never returns made-up data.

This page explains the four parts that make that work: versions, triage, repairs, and the fast path.

## Versions

Every change to a skill's steps is saved as a new, numbered **version**. That includes the first recording, each automatic repair, each fast path, each edit you make, and each restore. A version records:

- **Why it was made**: for example `initial`, `heal_fp`, `heal_ai`, `fetch`, `edit`, or `restore`.
- **The run that caused it**, if there was one.
- **The full steps at that point.** It is a complete copy, not just the changes, so an old version can always be replayed exactly.

What you can do with versions:

- **Compare** any two versions to see which steps and settings changed.
- **Restore** an older version. The restore is saved as a new version, so nothing is lost.
- **Pin** a skill to a version. A pinned skill keeps running that version. Automatic repairs are still saved, but as *candidate* versions for you to review. They do not change what runs.
- **Run one version for one call** by passing `version`, without pinning.

To do these from code, see the [Skill versions API](/api-reference/versions/list). To compare and roll back after an improvement, see [Improve a skill](/guides/improve-a-skill#compare-pin-or-roll-back).

## Why runs fail

When a run fails, Valendata first works out why. Each failed run gets exactly one **failure kind**, returned as `triage_kind` on the result:

| Kind | What it means | Is it repaired? |
| --- | --- | --- |
| `site_down` | The site did not respond, or returned a server error. | No. The run may wait and try once more, then fails and reports the reason. |
| `blocked` | The site refused access, or asked for a check that a person must complete. | No. The run fails and reports the reason. |
| `logged_out` | The site asked for a sign-in where data was expected. | No. Valendata tells you to sign in again. See [Logins and browser profiles](/concepts/logins-and-browser-profiles). |
| `page_not_loaded` | The page came back blank or incomplete. | No. The run may wait and try once more, then fails and reports the reason. |
| `element_changed` | The page loaded, but a recorded element was not there. | Yes. See [Repairs](#repairs). |
| `extraction_drift` | The steps ran on a real page, but the rows came back empty or hollow. | Yes. See [Repairs](#repairs). |
| `unknown` | None of the above matched. | Reported. |
| `ok` | The run did not fail. | Not needed. |

This order matters. Repairing a skill never fixes a site that is down, a sign-in that has expired, or a site that is refusing access. Trying to would waste your credits, and could replace good steps with bad ones. So these runs stop and report why, and nothing is changed.

## Repairs

Only `element_changed` and `extraction_drift` failures are repaired. Valendata tries the cheapest fix first:

1. **Code fix.** Valendata saved a fingerprint of each element when the skill was created. It looks for the element on the new page that best matches that fingerprint. This does not use an AI model, and it adds almost no time to the run. If it succeeds, the result reports `heal_kind: "fp"`.
2. **AI repair.** If the code fix cannot find a confident match, an AI agent works out the step on the changed page. If it succeeds, the result reports `heal_kind: "ai"`. Only one repair runs on a skill at a time, and each skill has a small daily limit on AI repairs. A skill that needs rescuing many times a day is flagged as broken, not hidden.

### Every repair is proven

A repair is accepted only if the rows it produces pass these checks:

- Rows exist.
- The contracted fields are not all empty.
- Every row has every field in the skill's output contract.
- The result is not clearly worse than any of the skill's last five good runs. A good run with the same inputs is compared on row count and fields. A good run with other inputs is compared on the fields both share: a field that run filled on most rows must not come back nearly empty. This uses what those runs already stored. No extra run is made.

A repair that fails these checks is thrown away, and the run reports the failure honestly. A repair that passes becomes a new version. You can review it, compare it, and roll it back.

Every result also says how far you can trust each field. See [Runs](/concepts/runs#how-far-to-trust-the-rows).

### Rows that look wrong

A run can return rows that are not really data. Valendata checks the rows of every run, and of every test before a skill goes live, using only that one run:

- **Repeated rows**: most rows, or every row, are the same record. This usually means the skill reads one card over and over. Valendata counts this before it removes duplicates, so the problem is not hidden.
- **Pages that repeat**: page 2 repeats the rows of page 1. This usually means the next-page step reloads the same page.
- **Placeholder values**: a field holds text like "See options", "N/A" or "—", or its own label, on most rows.

These show in the run's `diagnosis` as `quality_flags` (`repeated_rows`, `pagination_overlap`, `placeholder_values`). A test does not accept a skill whose rows are all the same record. The other checks are warnings shown next to the rows.

## Cookie and consent banners

When a skill runs in a cloud browser, Valendata clears cookie and consent banners after each page load. It recognizes common consent tools (OneTrust, Cookiebot, Didomi, Quantcast, TrustArc and others), Google's "Before you continue" page, and other cookie pop-ups in several languages. It clicks the site's own button. By default this is "Reject all" or "Only necessary", and "Accept" if there is no reject button. This uses no AI model.

A recorded click on a consent button, such as "Accept all", is optional. If the banner is not there, the step is skipped. It does not fail the run or start a repair. Your own Chrome is never changed: banners are only cleared in the cloud browser.

## Fast path

Many websites load their data from their own backend after the page opens. When a skill runs in a cloud browser, Valendata watches for a request that clearly carries the data the skill returns. If it finds one, it tests that request alongside normal runs. Only after the results keep agreeing does it become the skill's **fast path**, saved as a new version.

Other websites send the rows inside the page itself. For these, Valendata checks whether the list page can be downloaded with a plain web request, without a browser. Its address must follow the skill's inputs. The skill's own way of reading rows must also give the same rows as the browser run. This tries the page markup first, then any data block in the page. If it works, it is tested alongside normal runs in the same way, then saved as a new version.

From then on, each run tries the quickest route first and falls back in the same call if it has to:

1. **Direct HTTP** (`fetch_direct`): no browser.
2. **In-browser fetch** (`fetch_browser`): the same request, made from a browser.
3. **Page download** (`html_direct`): the list page's HTML, downloaded without a browser and read the same way the browser run reads it.
4. **Browser replay** (`replay`): the full recorded steps.

The page download goes through the same proxy the skill's browser would use, with an ordinary browser's request headers. It never sends your cookies. It is skipped when the skill's browser profile is signed in to the site. A sign-in page, a consent page, or a bot check is treated as a failure, and the run uses the browser instead. A page download costs no browser time.

Sites that build their rows with JavaScript, such as Google Maps, have no page download. Sites that block plain web requests keep using the browser.

A fast path that keeps failing is paused, and runs use the browser until the fast path is proven again. Each result reports `tier_used` and `tier_timings`. `GET /v1/skills/{slug}/health` shows how each route has done over the last 20 attempts.

## Where to see it

- **Each run result**: `triage_kind`, `heal_kind`, `recipe_version`, `tier_used`, and the trust fields.
- **[`GET /v1/skills/{slug}`](/api-reference/skills/get)**: `reliability`, `recipe_version`, `pinned_recipe_version`, and `fast_path`.
- **[`GET /v1/skills/{slug}/health`](/api-reference/skills/health)**: success rate and repairs over the last 20 runs, the last failure kind, and health for each route.
- **AI assistants**: each `skill_<slug>` tool's description includes the same short track record. See [MCP tools](/ai-assistants/mcp-tools).
