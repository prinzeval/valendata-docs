title: "Keeping skills working"
description: "Websites change. Valendata versions every skill, works out why a run failed, repairs only what can be repaired, checks each repair, and runs each skill on the fastest tier that works."
---

A skill saves the steps to take on a website and how to read the results. Websites change their layout, and steps that worked yesterday can break today. Valendata is built so that a skill either keeps returning correct rows or tells you clearly why it cannot. It never returns made-up data.

This page explains the four parts that make that work: versions, triage, repairs, and speed tiers.

## Versions

Every change to a skill's steps is saved as a new, numbered **version**. That includes the first recording, each automatic repair, each faster way to read the site, each edit you make, and each restore. A version records:

- **Why it was made**: the first recording, an automatic repair, a faster way to read the site, an edit of yours, or a restore. The API returns it as `reason`.
- **The run that caused it**, if there was one.
- **The full steps at that point.** It is a complete copy, not just the changes, so an old version can always be replayed exactly.

What you can do with versions:

- **Compare** any two versions to see which steps and settings changed.
- **Restore** an older version. The restore is saved as a new version, so nothing is lost.
- **Pin** a skill to a version. A pinned skill keeps running that version. Automatic repairs are still saved, but as *candidate* versions for you to review. They do not change what runs.
- **Run one version for one call** by passing `version`, without pinning.

To do these from code, see the [Skill versions API](/api-reference/versions/list). To compare and roll back after an improvement, see [Improve a skill](/guides/improve-a-skill#compare-pin-or-roll-back).

## Why runs fail

When a run fails, Valendata first works out why. Each failed run gets exactly one **failure kind**, returned as `triage_kind` on the result:

| Kind | What it means | Is it repaired? |
| --- | --- | --- |
| `site_down` | The site did not respond, or returned a server error. | No. The run may wait and try once more, then fails and reports the reason. |
| `blocked` | The site refused access, or asked for a check that a person must complete. | No. The run fails and reports the reason. |
| `logged_out` | The site asked for a sign-in where data was expected. | No. Valendata tells you to sign in again. See [Logins and browser profiles](/concepts/logins-and-browser-profiles). |
| `page_not_loaded` | The page came back blank or incomplete. | No. The run may wait and try once more, then fails and reports the reason. |
| `element_changed` | The page loaded, but a recorded element was not there. | Yes. See [Repairs](#repairs). |
| `extraction_drift` | The steps ran on a real page, but the rows came back empty or hollow. | Yes. See [Repairs](#repairs). |
| `unknown` | None of the above matched. | Reported. |
| `ok` | The run did not fail. | Not needed. |

This order matters. Repairing a skill never fixes a site that is down, a sign-in that has expired, or a site that is refusing access. Trying to would waste your credits, and could replace good steps with bad ones. So these runs stop and report why, and nothing is changed. If a site keeps refusing your skills, check how it is doing for others and ask us to make it work. See [When a site does not work](/guides/when-a-site-does-not-work).

## Repairs

Only `element_changed` and `extraction_drift` failures are repaired. A repair starts when one of your runs breaks, and it is charged like any run. When a run was repaired, its result says so in `heal_kind`.

### Every repair is proven

A repair is accepted only if the rows it produces pass these checks:

- Rows exist.
- The contracted fields are not all empty.
- Every row has every field in the skill's output contract.
- The result is not clearly worse than the skill's recent good runs: no fewer rows for the same inputs, and no field that used to be filled coming back nearly empty.

A repair that fails these checks is thrown away, and the run reports the failure honestly. A repair that passes becomes a new version. You can review it, compare it, and roll it back.

Every result also says how far you can trust each field. See [Runs](/concepts/runs#how-far-to-trust-the-rows).

### Rows that look wrong

A run can return rows that are not really data. Valendata checks the rows of every run, and of every test before a skill goes live, using only that one run:

- **Repeated rows**: most rows, or every row, are the same record. This usually means the skill reads one card over and over. Valendata counts this before it removes duplicates, so the problem is not hidden.
- **Pages that repeat**: page 2 repeats the rows of page 1. This usually means the next-page step reloads the same page.
- **Placeholder values**: a field holds text like "See options", "N/A" or "—", or its own label, on most rows.

These show in the run's `diagnosis` as `quality_flags` (`repeated_rows`, `pagination_overlap`, `placeholder_values`). A test does not accept a skill whose rows are all the same record. The other checks are warnings shown next to the rows.

## Talk to a skill

Each skill has its own chat at the top of its page. Say what is wrong or what you want in plain words, such as "the last run missed the phone numbers" or "also get the price". The skill looks at its own runs and versions and fixes itself when it can. When only you can fix it, such as signing in again, it tells you. Each repair is checked before it is kept, and the result is posted to the chat. Repairs are charged like any run. New fields you ask for are charged as an [improvement](/guides/improve-a-skill).

From code, use [Talk to a skill](/api-reference/improvements/talk). An AI assistant uses the `talk_to_skill` tool.

### A skill built on an open API

A skill built on the site's [open API](/guides/create-a-skill#open-apis-first) has no browser steps, so its repairs work on the API. When one of its runs fails or comes back with fields missing or wrong, the skill repairs itself on the API, charged like any run. If the site no longer has an open API that fits, it tells you in the skill's chat and offers to record the skill in a browser. Nothing is recorded until you say yes. What each repair mode does is in [Skills built on an open API](/guides/improve-a-skill#skills-built-on-an-open-api).

## Cookie and consent banners

In the cloud browser, cookie and consent banners are closed for you after each page loads. Valendata clicks the site's own button: "Reject all" or "Only necessary" when there is one, else "Accept".

A recorded click on a consent button, such as "Accept all", is skipped when the banner is not there. It does not fail the run. Your own Chrome is never changed.

## Speed tiers

Every skill runs on one of three tiers:

| Tier | Time | How it reads |
| --- | --- | --- |
| Tier 1 | about 1 second | The site's data, read without a browser. |
| Tier 2 | a few seconds | The same data, read through a browser: the cloud browser or your Chrome. |
| Tier 3 | about a minute | The skill's recorded steps, in a browser. |

When a skill is made, Valendata tries the fastest tier and uses it only once it gives the same rows as the skill's normal run, on more than one search. The message that says the skill is ready names its tier. Some sites have no faster way; their skills stay on Tier 3.

A skill stays on its tier. When its faster read does not work on a run, the same run still returns rows the slower way, so the run does not fail for that. Every change of tier is listed in the skill's **Speed** tab, under **What happened**.

You can also try a faster tier yourself, or choose the tier a skill runs on, from the **Speed** tab, [the API](/api-reference/skills/try-speed) or an AI assistant. A tier must work before you can choose it. A skill that signs in to a site stays in its browser.

A faster tier never sends your cookies. A tier that needs no browser costs no browser time.

### Runs Valendata starts itself

Some runs are Valendata's own checks, not yours: a **creation test** (when a skill is made), a **repair check** (while a repair is proven) and a **speed trial** (while a faster tier is proven). Each run says which it is in `run_kind` and `run_kind_label`, and these runs never count toward a skill's success rate.

## Where to see it

- **Each run result**: `triage_kind`, `heal_kind`, `recipe_version`, `tier`, `read_way`, `run_kind`, and the trust fields.
- **[`GET /v1/skills/{slug}`](/api-reference/skills/get)**: `reliability`, `recipe_version`, `pinned_recipe_version`, `fast_path`, and `reads_by`.
- **[`GET /v1/skills/{slug}/health`](/api-reference/skills/health)**: success rate and repairs over the last 20 runs, the last failure kind, and health for each route.
- **[`GET /v1/skills/{slug}/speed`](/api-reference/skills/speed)** and the skill's **Speed** tab: the tier it runs on, how each tier is doing, the latest speed trial, and what has changed. Its **Technical details** show how each tier reads and, for a skill built on an open API, the API address, where it was found, where each field comes from in the answer, how it reads more pages, and how its calls have done.
- **AI assistants**: each `skill_<slug>` tool's description includes the same short track record. See [MCP tools](/ai-assistants/mcp-tools).
