title: "Logins and browser profiles"
description: "Two ways a skill gets past a sign-in page: a browser profile that is already signed in, or a saved login the run uses to sign in itself."
---

Much useful data sits behind a sign-in: your orders, a dashboard, a members-only list. A skill can reach it in two ways, and they work together.

| | Browser profile | Saved login |
| --- | --- | --- |
| What it is | A browser's signed-in state (cookies and storage), kept in the cloud. | A username and password (and optional authenticator seed), encrypted. |
| How it signs in | It does not need to. The site sees a session that is already signed in. | The run types the login in, only when the site asks. |
| Good for | Sites with SSO, hardware keys, or checks a run cannot pass. | Sites where sessions expire often. |
| Shared? | Belongs to a workspace. | Personal. Never shared with your workspace. |

A run first checks the start page. If the browser profile is already signed in, it just reads the page. If the site asks for a sign-in and the skill has a saved login, the run signs in once and carries on. If it still cannot get in, it stops and tells you why. It never retries in a loop.

To set either one up, see [Use a saved login](/guides/use-a-saved-login).

## Browser profiles

A **browser profile** stores a browser's signed-in state. Every workspace has a **Default** profile, used by cloud runs unless a skill picks another one. You can also pick a profile per workflow step, so different steps run as different accounts.

Each profile has an **exit IP**: the country the site sees. Keep it the same as where you first signed in. A mismatch can make the site end the session. If you imported your sign-in from your own Chrome, leave it on **No proxy**.

Sessions expire. When one does, runs fail with `triage_kind: "logged_out"` and you get a notice to sign in again on that profile.

## Saved logins

A **saved login** is encrypted and shown only masked (`to***h`). Your password, authenticator seed, and sign-in codes:

- never reach the AI model that drives the browser. It sees placeholders such as `vault_password`, and the real value is typed only on the login site.
- are never written to logs, run results, rows, webhooks, or AI assistant results.
- are never recorded while the run signs in.
- are never shared with your workspace.

While it signs in, the browser is fenced to the login site, so a page cannot send it somewhere else with your details.

Only **your own** runs sign in. A teammate running a shared skill, an API key without the `logins:use` scope, or anyone running a public copy of the skill gets `needs_user.kind = "no_login"` instead. A copied skill never carries your login.

A login is a setting on a skill, not a tool. No AI assistant can ask Valendata to "log in somewhere", and nothing can read a saved password back.

### Does a skill need a login?

Every skill says so in `login_need`, with the site in `login_site`:

| `login_need` | Meaning |
| --- | --- |
| `required` | The site asked for a sign-in: its recording signed in, a run met a login wall, or its first page showed one to a signed-out visitor. Bring your own login for `login_site`: sign in to it in your Chrome, or save it here and pick it on the skill. |
| `optional` | It can sign in when the site asks, but a run also worked without a login. |
| `none` | A run worked with no login and nothing ever asked for one. |
| `unknown` | Not known yet. It is never a promise that no login is needed. |

A required skill run with no usable login stops before it starts, so it costs nothing.

### Your own account

A skill that can sign in (`login_need` is `required` or `optional`) always runs on your own account, with your own access. Its `login_notice` says so, for example:

> Runs on your own linkedin.com account, with your own access. linkedin.com may limit or restrict accounts that are automated. Valendata never supplies or shares accounts.

Show it as it is wherever you show the skill. A skill that never signs in has `login_notice: null`.

No run uses a saved login until you confirm once that it is your own account:

- In the app, tick **This is my own account** when you save the login in the **Vault**. A login saved earlier has a **Confirm** button there.
- Over the API, send `"acknowledged": true` with [Create a login](/api-reference/logins/create) (without it the login is refused with `422`), or confirm an existing login with [Update a login](/api-reference/logins/update). Every login shows `acknowledged`.

Until then, a run that needs the login stops with `needs_user.kind = "login_not_acknowledged"`.

Two runs never drive the same saved login at once (they would break each other's session), so a run waits until no other run is using that login. Different logins run side by side.

With **polite pace** on, runs on the login also start at least a minute apart (30 seconds on X), the way a person uses a site. It lowers the chance the site restricts the account; turn it off for speed, and runs on the login go back to back. Every login shows `polite_pace`. It is on by default for linkedin.com, instagram.com, facebook.com, x.com and twitter.com and off everywhere else; change it with the **Polite pace** switch in the **Vault** or with [Update a login](/api-reference/logins/update).

How you use your accounts is your responsibility under the [Terms](https://valendata.com/terms-and-conditions): you confirm each login is your own, Valendata keeps the record of your runs, and it cooperates with lawful requests.

### Several logins for one site

You can save more than one login for the same site, for example a work and a personal account. A run picks one this way:

1. The login chosen on the skill always wins.
2. With only one saved login for the site, it is used without asking.
3. With several, the site's **default** is used. Mark it with the star on the login in the **Vault**, or send `"is_default": true` with [Create a login](/api-reference/logins/create) or [Update a login](/api-reference/logins/update). A site has one default; making a new one clears the old.
4. Otherwise the run stops with `needs_user.kind = "choose_login"` and lists the site's logins, masked:

```json
{
  "needs_user": {
    "kind": "choose_login",
    "site": "linkedin.com",
    "message": "You have several saved logins for linkedin.com and none is chosen. Which one should it use?",
    "options": [
      {"login_id": "lgn_1…", "username_hint": "ad***a", "label": "Work"},
      {"login_id": "lgn_2…", "username_hint": "ad***2", "label": "Personal"}
    ]
  }
}
```

Pick one in the app and it is saved on the skill, so that skill never asks again. Tick **Make it the default for** the site and no skill asks again. Over the API or MCP, pass the option's `login_id`: on the skill with [Update a skill](/api-reference/skills/update) (MCP: `update_skill`), or when you create one with [Create a skill](/api-reference/skills/create) (MCP: `create_skill`).

Each saved login has its own browser profile (`profile_id`, read-only), so two accounts on the same site never share cookies.

### Two-step sign-in

| What the site asks | What happens |
| --- | --- |
| A code from an authenticator app | Add the authenticator seed (`totp_secret`) to the login. The run works out the current code. |
| A code sent by email | If the site account uses your Valendata email, the run reads the code from your inbox; if it uses your connected Gmail or Outlook, the run reads it there. Any other address stops with `otp_email`. |
| A code sent by text or a phone app | The run waits up to 10 minutes for you to enter it, in the app or with [Send a sign-in code](/api-reference/runs/send-code). No code in time gives `otp_sms`. |
| A texted code you forward from your phone | An iPhone Shortcut or an Android automation sends the message to [`POST /v1/logins/{login_id}/code`](/api-reference/logins/send-code) (setup on that page). The run signing in with that login takes it. The Vault shows each login's address under **How sign-in codes work**. |
| Codes your own systems receive | Give the login a `code_url`: your own public `https` address. While a run waits for a code, Valendata sends a `POST` there every 10 seconds with `{"type": "sign_in_code_request", "login_id", "site", "run_id"}`, signed like [webhooks](/api-reference/webhooks/overview#verify-the-signature) (`X-Valendata-Signature`, same secret). Answer `{"code": "..."}` (the whole message is fine), or `204` while there is none yet. Public hosts only; redirects are not followed. Set it with [Create a login](/api-reference/logins/create) or [Update a login](/api-reference/logins/update); `""` removes it. |

### When a run cannot sign in

The run fails with `triage_kind: "login_failed"` (or `"logged_out"` when there is no login to use) and a `needs_user` object:

```json
{
  "status": "failed",
  "triage_kind": "login_failed",
  "needs_user": {
    "kind": "bad_password",
    "message": "The site did not accept the saved login. Check the username and password in the Vault, then run it again.",
    "action_url": "/vault"
  }
}
```

| `needs_user.kind` | What to do |
| --- | --- |
| `choose_signup_email` | The site needs an account and none is saved: say which email to register it with (see below). |
| `no_login` | Save the site's login and pick it on the skill, or this caller may not use it. |
| `bad_password` | Fix the username or password in the **Vault**. |
| `otp_email` | Use your Valendata email on the site account, or sign in once on the skill's browser profile. |
| `otp_sms` | Run it again and enter the code when asked, or add the authenticator seed. |
| `captcha` | Sign in once on the skill's browser profile, then run it again. |
| `login_not_acknowledged` | Confirm the login is your own account (see [Your own account](#your-own-account)). |
| `choose_login` | Several saved logins fit the site and none is chosen: pick one (see [Several logins for one site](#several-logins-for-one-site)). |

You also get an inbox note with a link to the **Vault**. Valendata never asks for your password in a chat.

### When a site needs an account that does not exist yet

A skill, a workflow step, a chat agent or a run that meets a sign-in on a site with no saved login never guesses. It asks you once, per site: **"Which email should I use for this site — your own Gmail (connected app) or the email Valendata provides?"** The question is a card in the app (the skill page, the creation progress, the chat, the workflow panel), and over the API it is the run's or creation's `needs_user`:

```json
{
  "needs_user": {
    "kind": "choose_signup_email",
    "site": "glassdoor.com",
    "card_id": "0b7c…",
    "question": "Which email should I use for glassdoor.com — your own Gmail (connected app) or the email Valendata provides?",
    "options": [
      {"value": "own", "label": "My Gmail (ada@gmail.com)", "address": "ada@gmail.com", "app": "gmail"},
      {"value": "valendata", "label": "Valendata email (ada@mail.valendata.com)", "address": "ada@mail.valendata.com"}
    ]
  }
}
```

Your own address is offered only while a Gmail or Outlook is connected (otherwise `connect_url` says where to connect one). Answer the card in the app, or with [Answer a question card](/api-reference/logins/answer-question) (MCP: `answer_questions`), passing the option's label as shown. The moment you answer, the site's login is saved to your **Vault** (your chosen address and a generated password, marked *created by Valendata*); run or create again and the run registers the account with it, reads the emailed code or link from that address's inbox, and signs in. Every later run signs in with that saved login.

Tick **Always use this for new sites** and no site asks again: the choice is kept on your persona under **Create accounts automatically** (Persona → Permissions → *Email for new accounts*), where you can change it or go back to *Ask me each time* — or over the API with [Get](/api-reference/account/get-signup-email) / [Set the sign-up email default](/api-reference/account/set-signup-email) (MCP: `get_signup_email`, `set_signup_email`). A run with nobody watching (a schedule, the API, MCP) uses that saved choice; without one it stops with the same question.

## Cost

Signing in is part of the run: its browser time and AI steps are billed like any other step. A profile that is already signed in costs nothing extra.
