Tool names follow the API: `list_`, `get_`, `search_`, `create_`, `update_`, `delete_`, plus one tool per skill (`skill_<slug>`) and per workflow (`workflow_<slug>`). Each tool does the same thing as the API call in its last column, so the API page has the full fields.

Each argument has one name on every tool: `skill` for a skill's slug, and `browser` (`auto`, `cloud`, or `extension`) for where it runs. Workflow tools take the workflow's `slug`. The API's spelling works too: `slug` on a skill tool reads as `skill`, and `browser_type` reads as `browser` (its `remote` as `cloud`). Sending both names with different values is refused.

For how to connect, see [Connect your AI assistant](/ai-assistants/connect). For what each tool changes and costs, see [Limits and side effects](/ai-assistants/limits-and-side-effects).

## Which tools the assistant sees

The assistant only sees the tools its connection's scopes allow, so the list grows with what you grant. A default assistant connection (OAuth, nothing ticked under **Optional extra access**) sees these tools, plus one tool per skill and per workflow:

- **Find**: `search_skills`, `search_workflows`, `site_status`, `request_site`.
- **Skills**: `list_skills`, `get_skill`, `clone_skill`, `run_skill`, `run_skill_batch`, `get_batch`, `create_skill`, `get_skill_creation`, `list_skill_creations`, `improve_skill`, `get_skill_improvement`, `talk_to_skill`, `stop_skill_doctor`, `cancel_skill_creation`, `list_skill_versions`, `compare_skill_versions`, `list_batches`, `cancel_batch`, `list_skill_runs`, `list_site_apis`, `call_site_api`.
- **Logins**: `list_logins`, `list_profiles`, `get_question`, `answer_questions`.
- **Workflows**: `list_workflows`, `get_workflow`, `get_workflow_webhook`, `clone_workflow`, `run_workflow`, `list_workflow_runs`, `list_workflow_versions`, `compare_workflow_versions`, `get_workflow_chat`.
- **Runs and schedules**: `list_runs`, `get_run`, `cancel_run`, `resume_run`, `list_schedules`.
- **Web pages**: `scrape_url`, `search_web`, `map_site`, `crawl_site`, `get_crawl`, `extract_data`, `get_extract`.
- **Knowledge**: `get_knowledge`, `save_knowledge`.

`update_skill`, `delete_skill`, `delete_unused_archived_skills`, `update_from_marketplace`, `schedule_skill`, `try_skill_speed`, `use_skill_speed`, `restore_skill_version`, and `pin_skill_version` appear only with `skills:write`. `create_workflow`, `update_workflow`, `delete_workflow`, `schedule_workflow`, `restore_workflow_version`, `talk_to_workflow`, `stop_workflow_doctor`, `update_schedule`, and `delete_schedule` appear only with `workflows:write` (`update_schedule` and `delete_schedule` also with `skills:write`). `get_account`, `get_usage`, and `get_signup_email` appear only with `account:read`. `set_signup_email` needs `logins:write`, which only an API key can hold. The connected-app tools appear only with `apps:read` (`act_in_app` and `disconnect_app` only with `apps:write`). `list_followups` and `get_followup` appear only with `followups:read`, `create_followup` and `cancel_followup` only with `followups:write`. `list_jobs` and `get_job` appear only with `jobs:read`, `start_jobs` and `cancel_job` only with `jobs:write`. `list_notes` and `get_note` appear only with `notes:read`, `create_note`, `update_note`, and `delete_note` only with `notes:write`. `search_skills`, `search_workflows`, and `site_status` are listed for every connection, whatever its scopes. An API key sees the tools its own scopes allow. The tables below give each tool's scope.

`get_skill` lists the skill's [available inputs](/concepts/skills#available-inputs) in its text, each with how it acts and whether it is on, for example `Available inputs: department (filter, off), q (request, on).` To turn one on, the assistant sends that entry from `available_inputs` in `update_skill`'s `inputs.add`; to turn it off, its name in `inputs.remove`. `update_skill` also changes an output field's type with `outputs.update`, and sets `row_key`, the fields that tell rows apart when runs are compared (see [Only what's new](/guides/schedule#only-whats-new)). See [Update a skill](/api-reference/skills/update#inputs).

`delete_unused_archived_skills` clears your **Archive**: it deletes every archived skill you own that nothing uses. A skill that a workflow, a schedule, an API key, or the marketplace still uses is kept, and the answer says what uses it. Live skills, drafts, and other people's skills are never touched, and runs are kept. It cannot be undone, so the assistant calls it with `dry_run: true` first, shows you what would go, and deletes only on your yes.

Over OAuth, `skills:invoke` lets an assistant run skills and also create and improve them (`create_skill`, `get_skill_creation`, `list_skill_creations`, `improve_skill`, `get_skill_improvement`, `talk_to_skill`). Changing, deleting, and scheduling skills need `skills:write`, which you tick on the consent screen under **Optional extra access** ("Create, edit and delete your skills"). It is never granted by default.

`create_skill` answers at once. While the creation is `queued`, `recording`, or `validating`, the assistant calls `get_skill_creation` about every 30 seconds and passes on its `progress` line. A `queued` creation may be waiting for a free browser; nothing is charged while it waits. When the site has an open API, the skill is built on it with no browser, and the result's `source` is `api`. It stops at `ready`, `needs_fix`, or `failed` and follows `next_step`. On `needs_fix` the draft is fixed with `improve_skill`, not created again. Once it is `ready`, the assistant runs it with `run_skill`. See [Create a skill](/guides/create-a-skill#from-a-sentence).

### A tool for each of your most used skills: `skill_<slug>`

Your 20 most used skills (the most recently run first, then the most run) are each their own tool, named `skill_` plus its slug. Every other skill runs with `run_skill` by slug: find it with `search_skills` or `list_skills`. This keeps the assistant's tool list short however many skills you have, so it does not fill the assistant's memory before it starts. A call to any skill's own tool still works, listed or not. A skill with the slug `austin-dentists` becomes `skill_austin-dentists`. The list holds skills you own and skills shared into your workspaces. A marketplace skill appears here once you clone it.

Each tool has:

- **A description**: what the skill does, a short track record (runs, recent success rate, typical time and row count, the last error, and its [speed](/api-reference/skills/speed) when it is faster than a browser), and what a run usually costs, for example "About 6 credits (\$0.06) per run." See [Price](/api-reference/skills/get#price).
- **An input schema**: the skill's own inputs, plus optional `max_results` (0–500, `0` for the whole list), `version`, `browser`, `idempotency_key`, `max_age`, `details`, `detail`, `fields`, `start_page`, `changes_since`, `delivery`, and `watch` (see [Run results](#run-results)). A skill input with the same name as one of these stays the skill's input.
- **An output schema**: the row shape, so the assistant can rely on field names.

Listing needs `skills:read`. Calling needs `skills:invoke`. It works like [Run a skill and wait](/api-reference/runs/run-skill), with the wait described in [Run results](#run-results). The list is rebuilt each time the assistant refreshes it, so a new skill shows up on the next refresh.

`run_skill` (`slug` or id, optional `inputs`, `max_results`, `version`, `browser`, `idempotency_key`, `max_age`, `details`, `detail`, `fields`, `changes_since`, `delivery`, `watch`) runs any skill you can run, the same way. Use it for a skill created or fixed in this chat: the assistant's tool list only refreshes when a new chat starts. The owner can also test-run a `needs_fix` draft with it.

`run_skill` does not run a public marketplace skill you have not cloned. It answers `not_found` with `'<slug>' is a public marketplace skill you have not cloned. Clone it first with clone_skill(skill="<slug>"), then run the copy's slug.` and `next_step` set to `clone_skill(skill="<slug>")`.

## Marketplace

| Tool | Arguments | Scope | Same as |
| --- | --- | --- | --- |
| `search_skills` | `query` (the task, in plain words), optional `site`, `category`, `limit` | None. With `skills:read` it also searches your own skills and your workspaces'. | [Find a skill for a task](/api-reference/marketplace/search) |
| `search_workflows` | `query` (the task, in plain words), optional `limit` | None. With `workflows:read` it also searches your own workflows and your workspaces'. | [Find a skill for a task](/api-reference/marketplace/search#workflows) with `kind=workflow` |

Its structured content is the API's answer, with each skill's `sample_rows` and `clone_url`. Its text lists one skill per line: the slug, name and site, "About N credits (\$X) per run", its [track record](/guides/use-the-marketplace#track-record) (for a public skill, for example "track record: Working: worked 18 of the last 20 runs (90%) · typical run 6.2 s · last worked 2 h ago · checked 2 h ago"; for your own private skill, what percent of its last 20 runs worked), and its inputs (`*` marks a required one). A skill that is not yours ends with "Not yours: clone it first." The text ends with how to run yours, `run_skill(skill=...)`, and how to clone the others, `clone_skill(skill=...)`, or, when nothing does the task exactly, the hint that `create_skill` can record it.

An assistant can read everything public about a marketplace skill: its inputs, sample rows, price, and health. It runs only its own skills and its workspaces'. To use a marketplace skill:

1. Find it with `search_skills`. Read its inputs, `sample_rows`, price, and track record, or call `get_skill` for the full contract. The text of `get_skill` has the same "Track record:" line for a public skill.
2. Copy it with `clone_skill`. Cloning is free. The answer says `Cloned <slug> as <new slug>. Run it with run_skill(skill="<new slug>").`
3. Run the copy with `run_skill` and its new slug.

`search_workflows` does the same for workflows. Its text lists one workflow per line: the slug, name, "About N credits (\$X) per run", how many runs it has had so far, and its inputs. One that is not yours ends with "Not yours: clone it first." The text ends with what to do next. To use a marketplace workflow:

1. Find it with `search_workflows`.
2. Read it with `get_workflow`. A public workflow shows its steps in plain words, its sample rows, what it needs, and its price. See [Get a workflow](/api-reference/workflows/get#a-public-workflow).
3. Copy it with `clone_workflow`. Cloning is free.
4. Run the copy with `run_workflow` and its new slug.

## Many inputs at once: batches

A batch runs one skill once per input set, over a list of up to 10,000, a few at a time, in the background.

| Tool | Arguments | Scope | Same as |
| --- | --- | --- | --- |
| `run_skill_batch` | `skill`, `inputs` (one object of the skill's inputs per run, 1–10,000), optional `max_results_per_input` (1–500), `concurrency` (1–100, capped at your account's limit), `label`, `allow_partial` (default `false`) | `skills:invoke` | `POST /v1/skills/{slug}/batches` |
| `get_batch` | `batch_id`, optional `rows` (default `false`), `limit` (rows per page, 1–100, default 25), `cursor` | `runs:read` | `GET /v1/batches/{batch_id}`, and `GET /v1/batches/{batch_id}/rows` with `rows: true` |
| `list_batches` | optional `skill`, `open` (default `false`), `limit` (1–100, default 25), `cursor` | `runs:read` | [List batches](/api-reference/batches/list) |
| `cancel_batch` | `batch_id` | `skills:invoke` | [Cancel a batch](/api-reference/batches/cancel) |

Every input is checked first: one bad input refuses the whole list and nothing starts. `run_skill_batch` answers at once with the batch and its credit estimate (the same as `POST /v1/skills/{slug}/batches/estimate`). It is refused when your balance covers less than half the estimate, unless `allow_partial` is `true`; then it stops when the credits run out. Every input is charged like a single run.

The assistant polls `get_batch` until its status is no longer `queued` or `running`. It ends as `completed`, `cancelled`, `out_of_credits`, or `failed`, with how many inputs are done, the rows collected, and the credits used. With `rows: true` it adds a page of rows, each with `_input`, the input it came from; pass `rows_next_cursor` as `cursor` for the next page.

## Run results

### Waiting

`skill_<slug>`, `run_skill`, `call_site_api`, `workflow_<slug>`, and `run_workflow` start the run, then wait up to **75 seconds** for it. How waiting compares with a background run in general: [Runs](/concepts/runs#wait-or-run-in-the-background).

- **Done in time**: the result is the finished run.
- **Not done yet**: the result has `status: "running"` (or `queued` / `pending`), the `run_id`, and `next_step`: "Call get_run with this run_id in about 30 seconds; cancel_run stops it." The run keeps going and is billed as usual.
- **A workflow that needs a person** stops waiting at once, with `status: "waiting_for_human"` and a `next_step` telling the user to answer it in the Valendata app.

A client that sends a `progressToken` gets a progress notification about every 10 seconds while it waits.

### MCP Tasks

A client on a current MCP protocol version that declares the MCP Tasks extension (`io.modelcontextprotocol/tasks`) in its capabilities gets a task instead of a wait from `skill_<slug>`, `run_skill`, `call_site_api`, `workflow_<slug>`, `run_workflow`, `create_skill`, `improve_skill`, `try_skill_speed`, `run_skill_batch`, `crawl_site`, and `extract_data`, and from `talk_to_skill` when its answer started a repair that is still running (the task is that repair, with the skill's answer as its `statusMessage`). The call answers at once with `resultType: "task"` and a task:

| Field | What it is |
| --- | --- |
| `taskId` | The work's own id: the skill run id (`run_…`), the workflow run id with `wfrun_` in front, the creation id, the improvement id, the speed trial id (`st_…`), the batch id (`bat_…`), or the crawl or extract id with `wj_` in front. |
| `status` | `working` while it goes, then `completed` or `cancelled`. |
| `statusMessage` | One plain line, such as "Austin dentists is running." |
| `pollIntervalMs` | How often to poll: 5000 (5 seconds). |
| `createdAt`, `lastUpdatedAt` | When it started and last changed. |
| `ttlMs` | `null`: the task is kept, so you can read it later. |

Poll with `tasks/get` and the `taskId`. Once `status` is `completed`, its `result` is the same tool result the call would have given without the extension, including a run that failed, which still ends as `completed` with `status: "failed"` in its result. `tasks/cancel` stops a skill run, a workflow run, a speed trial, a batch, a crawl or an extract, and a skill creation while it is still recording. An improvement cannot be stopped once it has started. A stopped speed trial ends as `cancelled` and its skill stays on the tier it uses. A task is visible only to the person who started it; any other id answers `Unknown task`. Nothing here asks the client for input, so `tasks/update` is refused.

A client that does not declare the extension gets the 75-second wait above, the same as always. Every long tool's answer then carries `next_step`: the exact tool call that reads it and how long to wait. See [Hearing when a long job is done](/concepts/long-jobs).

### Which browser

The run, schedule, and `create_skill` tools take an optional `browser`:

- `auto` (default): the skill's own browser, else the cloud browser. In a workflow, each browser step uses its own, so steps may differ.
- `cloud`: the Valendata cloud browser.
- `extension`: your own Chrome with the Valendata extension. It must be connected, and it uses that Chrome's own sign-ins, which may be a different account. The assistant uses it only when you chose it.

The browser never changes by itself. When the cloud browser is paused, the call is refused with `cloud_browser_paused` and nothing is charged; the assistant tells you why and asks before calling again with `extension`. When your Chrome is not connected, the call is refused with `extension_not_connected`. A skill that signs in with a saved login or browser profile runs only on its own browser. More on where skills run: [Skills](/concepts/skills#where-a-skill-runs).

### Retry safely: `idempotency_key`

All four run tools take an optional `idempotency_key` (1–255 characters). Calling again with the same key returns the run that key first started, in its current state, with `idempotent_replay: true`. It never starts a second paid run. A key already used for a different skill or workflow is refused with `conflict`. This is the API's `Idempotency-Key`; see [Idempotency](/api-reference/pagination-and-idempotency#idempotency).

### Reuse a recent answer: `max_age`

Skill tools and `run_skill` take an optional `max_age` (seconds, 0–86400). When you ran the same skill with the same inputs within that time, the run is answered at once from that run's rows, for a share of the price. Leave it out to always run. See [Cached answers](/api-reference/runs/run-skill#cached-answers).

### Only what's new

Skill tools and `run_skill` take `changes_since` (`last` or a run id), `delivery` (`all`, `new`, or `changes`), and `watch` (such as `["price:down"]`); `schedule_skill` and `update_schedule` take `delivery`, `notify_on`, `watch`, and `webhook_url`. The answer and `get_run` then carry `changes`, and `get_run` with `changes: true` returns every new, changed, and removed row. What these mean and how runs are compared: [Only what's new](/guides/schedule#only-whats-new).

### What a skill run answers

A skill run's answer (from a skill tool, `run_skill`, or `get_run`) holds only what the assistant needs to act on:

| Field | What it is |
| --- | --- |
| `run_id` | The run's id. |
| `skill` | The skill's slug. |
| `status` | `queued`, `running`, `success`, `partial`, `failed`, or `cancelled`. See [Runs](/concepts/runs#status). |
| `count` | Rows the run produced in all. |
| `rows` | One page of those rows. |
| `has_more`, `next_offset` | `has_more` is `true` when there are more rows; call `get_run` with `offset` set to `next_offset`. |
| `error`, `error_code` | Why a failed run failed. `error_code` is `run_failed`, `needs_user`, `insufficient_credits`, or `spend_cap` (see [Errors](#errors)). |
| `credits_charged` | What the run cost. |
| `needs_user` | Set when the user must act (a login, a code, a human check): `kind`, `message`, `action_url`. |
| `diagnosis_summary` | Why rows came back short, in one line. |
| `next_step` | What to do next, in plain words. |

It also has `suggested_hint_examples` (hints for `improve_skill`) when there are some, `type_notes` when some values were kept as printed (see [Output field types](/concepts/skills#output-field-types)), and `idempotent_replay: true` on a replay. `get_run` adds `kind` (`skill` or `workflow`). A workflow run answers its own fields (`outputs`, `steps`, and the rest; statuses `pending`, `running`, `waiting_for_human`, `completed`, `failed`, `cancelled`), with each final step's rows paged the same way and `has_more`, `next_offset`, and `next_step` added.

### Less or more: `detail`, `details`, `fields`, `offset`, `limit`

| Argument | On | What it does |
| --- | --- | --- |
| `detail` | skill tools, `run_skill`, `get_run` | `summary` (default): the fields above. `full`: everything a skill run recorded, as [Get a run](/api-reference/runs/get) returns it (timings, cost estimates, field checks). |
| `details` | skill tools, `run_skill` | `true` (default): each row also has `details`, everything else the site had for it, under the site's own names. `false`: only the skill's own fields, for smaller answers. Not the same as `detail`. |
| `start_page` | skill tools | Start further into a paged list: a page number, or the `next_page` an earlier answer gave. |
| `fields` | skill tools, `run_skill`, `get_run` | Only these row columns, for example `["name", "phone"]`. A `price` field's `<field>_currency` comes with it. An unknown name is refused with `invalid_arguments`, and `details.valid_fields` lists the valid ones. |
| `offset` | `get_run` | First row to return. Default `0`. |
| `limit` | `get_run` | Rows per page. Default `100`, max `500`. |

A run tool answers the first 100 rows. For the rest, call `get_run` with `offset: next_offset`.

### The run as a resource

Every run is also a resource at `valendata://runs/{run_id}`, with optional `?offset=&limit=&fields=&detail=` (for example `valendata://runs/run_3f9a1c2b7d4e?offset=100&limit=100&fields=name,phone`). Reading it returns the same answer as `get_run`, with the same scope and owner checks. When a run has more rows than one answer holds, the tool result also carries a `resource_link` to the next page.

`create_workflow` with `task` builds the workflow from your skills in a few minutes and tests it once: the assistant polls `get_workflow` until `build.state` is `tested`, `needs_you`, or `failed`, and `build.said` says what was tested and what it costs. `app_trigger` starts the workflow when something happens in a connected app: `{app, trigger, config}` sets it (for example `app: "gmail"`), `{enabled}` alone pauses or resumes it, and `null` removes it. Each event starts a run that spends credits.

`talk_to_workflow` hands your message to the workflow's doctor, the same as the Brain chat in the builder. It answers at once; the doctor reads the runs, changes steps, and runs it again on its own. `next_step` says when to read its reply with `get_workflow_chat`. Every change it makes is kept as a version, so `restore_workflow_version` undoes it.

`workflows:write` is on API keys. For an assistant it is opt-in: tick "Create, edit and delete your workflows and schedules" under **Optional extra access** on the consent screen.

### One tool per workflow: `workflow_<slug>`

Every workflow you can run is its own tool, for example `workflow_competitor-prices`. Its input schema is the workflow's inputs plus optional `browser` and `idempotency_key`, and its output schema is the run. Calling it needs `workflows:invoke`. It works like [Run a workflow and wait](/api-reference/runs/run-workflow), with the wait described in [Run results](#run-results).

`run_workflow` (`slug` or id, optional `inputs`, `browser`, `idempotency_key`) runs any workflow you can run, the same way. Use it for a workflow made or cloned in this chat. A public marketplace workflow runs only once you copy it with `clone_workflow`; its answer says `Cloned <slug> as <new slug>. Run it with run_workflow(slug="<new slug>").`

Each workflow is also a resource at `valendata://workflows/{workflow_id}/latest`. Reading it returns the rows of its last finished run, at no cost. Needs `workflows:read`.

## Errors

Every failed tool call answers the same shape, as structured content and as JSON text:

```json
{
  "error": {
    "code": "invalid_arguments",
    "message": "Unknown field(s): email. Valid fields: name, phone, website.",
    "retryable": false,
    "retry_after_s": null,
    "next_step": "Call get_run with run_id \"run_3f9a1c2b7d4e\" and fields from valid_fields.",
    "details": {
      "unknown_fields": ["email"],
      "valid_fields": ["name", "phone", "website"],
      "run_id": "run_3f9a1c2b7d4e"
    }
  }
}
```

`details` is there only when there is more to say. `retryable` is `true` only for `capacity_full` and `internal`.

| `code` | Meaning | What the assistant should do |
| --- | --- | --- |
| `invalid_arguments` | An argument is wrong: a bad type or value, an unknown input or column. `details` names each problem. Nothing started. | Fix the arguments and call again. |
| `not_found` | No such skill, workflow, run, or schedule, or not one you can see. | Use `list_skills` or `list_workflows` to find the right one. |
| `missing_scope` | The connection lacks a scope. `details.scope` names it. | Tell the user to reconnect and tick that scope (or use a key that has it). |
| `key_not_allowed` | The API key is limited to other skills or workflows. | Tell the user; the key's limits are in **Settings → API Keys**. |
| `forbidden` | Not allowed, and no scope fixes it (for example, only the owner can delete it). | Tell the user. Do not retry. |
| `unauthenticated` | The call is not signed in. | Tell the user to reconnect Valendata. |
| `insufficient_credits` | Not enough credits to start. Nothing ran and nothing was charged. `details` has `current_balance` and `required`. | Tell the user to top up. Do not retry until they have. |
| `spend_cap` | The user reached their monthly spend cap in this workspace. Nothing ran. `details` has `cap` and `spent`. | Tell the user; the workspace owner can raise it. |
| `capacity_full` | Too many runs in progress. `retry_after_s` says how long to wait. | Wait `retry_after_s`, then call again with the same `idempotency_key`. |
| `run_failed` | The run ran and failed. | Follow `next_step`: usually `improve_skill`, or run again if it failed on our side. |
| `needs_user` | The user must act: a login, a code, a human check, or connecting an app. | Pass on the message and the link (`action_url`, or `connect_url` for an app), then run again. |
| `conflict` | The `idempotency_key` was already used for a different run, or the request clashes with the current state. | Use a new `idempotency_key` for a new run. |
| `cloud_browser_paused` | The run needs the cloud browser, which is paused right now. Nothing ran and nothing was charged. | Tell the user why, and ask before calling again with `browser: "extension"`. See [Which browser](#which-browser). |
| `extension_not_connected` | The run was sent to the user's Chrome, but the Valendata extension is not connected. Nothing ran. | Ask the user to open Chrome with the extension, then call again. Use `browser: "cloud"` only if the user says so. |
| `internal` | Something failed on our side. The message has a reference. | Try again shortly; if it keeps failing, give the user the reference. |

A run that started and then failed is not a tool error: its answer has `status: "failed"` and an `error_code` of `run_failed`, `needs_user`, `insufficient_credits`, or `spend_cap`, with the same meaning as above. A run is checked for credits before it starts, so `insufficient_credits` or `spend_cap` here means the balance ran out after it started.
