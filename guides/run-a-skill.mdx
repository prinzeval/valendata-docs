## In the app

Open the skill, fill in its inputs, and click **Run**. The rows appear in a table you can download. See [Export data](/guides/export-data).

## From the API

Before you start, create an API key in **Settings → API Keys** with the `skills:invoke` scope (and `runs:read` to read background runs). See [API keys](/account/api-keys).

To see what a skill takes and returns, read its contract with [`GET /v1/skills/{slug}`](/api-reference/skills/get): `input_schema` lists the inputs, `output_json_schema` the row shape.

Some inputs must be sent on every run, such as a hotel's check-in and check-out dates: without them the site shows no prices. They are listed in `input_schema` under `required`, with no default. A run that leaves one out, or sends a date that has passed, is refused with a `422` that names the input. Nothing runs and nothing is charged.

Send every date as `YYYY-MM-DD`, such as `2026-11-20`, whatever way the site writes dates. A date input has `"format": "date"` in `input_schema`, and its example is written the same way. Valendata writes the date the way the site does when the skill runs. A date written any other way is refused with a `422` that shows the format and an example. A date that looks ahead, such as a check-in or a departure, must be today or later. A date that looks back, such as "posted since" or one day's leaderboard, takes any day.

### Wait for the rows

[`POST /v1/skills/{slug}/run`](/api-reference/runs/run-skill) runs the skill and answers when it finishes. Put the inputs at the top level of the body:

<CodeGroup>

```bash curl
curl -X POST "https://api.valendata.com/v1/skills/austin-dentists/run?max_results=20" \
  -H "Authorization: Bearer $VALENDATA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"city": "Dallas"}'
```

```python Python
import os, requests

API = "https://api.valendata.com"
HEADERS = {"Authorization": f"Bearer {os.environ['VALENDATA_API_KEY']}"}

resp = requests.post(
    f"{API}/v1/skills/austin-dentists/run",
    headers=HEADERS,
    params={"max_results": 20},
    json={"city": "Dallas"},
    timeout=600,
)
resp.raise_for_status()
for row in resp.json()["data"]:
    print(row)
```

</CodeGroup>

The rows are in `data`. If your account already has as many runs in progress as it may, this call does not wait: it returns `429` with `Retry-After`. Run in the background instead.

### Run in the background

[`POST /v1/skills/{slug}/runs`](/api-reference/runs/start-skill-run) answers at once with a `run_id`. Inputs go under `inputs`. If your account is busy, the run waits in a queue.

<CodeGroup>

```bash curl
curl -X POST https://api.valendata.com/v1/skills/austin-dentists/runs \
  -H "Authorization: Bearer $VALENDATA_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1234" \
  -d '{"inputs": {"city": "Houston"}, "max_results": 50, "webhook_url": "https://example.com/hooks/valendata"}'
# → 202 {"run_id": "run_8c1d2e3f4a5b", "status": "queued", "poll_url": "/v1/runs/run_8c1d2e3f4a5b"}
```

```python Python
import os, time, requests

API = "https://api.valendata.com"
HEADERS = {"Authorization": f"Bearer {os.environ['VALENDATA_API_KEY']}"}

start = requests.post(
    f"{API}/v1/skills/austin-dentists/runs",
    headers={**HEADERS, "Idempotency-Key": "order-1234"},
    json={"inputs": {"city": "Houston"}, "max_results": 50},
).json()

while True:
    run = requests.get(f"{API}{start['poll_url']}", headers=HEADERS).json()
    if run["status"] not in ("queued", "running"):
        break
    time.sleep(3)

print(run["status"], run["count"], run["rows"][:3])
```

</CodeGroup>

Then either read [`GET /v1/runs/{run_id}`](/api-reference/runs/get) until `status` is no longer `queued` or `running`, or set `webhook_url` and Valendata sends you the finished run. See [Webhooks](/api-reference/webhooks/overview). In a finished background run, the rows are in `rows`.

To stop a run, call [`POST /v1/runs/{run_id}/cancel`](/api-reference/runs/cancel). To list a skill's past runs, call [`GET /v1/skills/{slug}/runs`](/api-reference/runs/list-skill-runs).

### Run one skill over many inputs

A **batch** runs one skill once for each input set in a list, such as 300 search words or 2,000 product links. It runs in the background, and all its rows come back as one result.

1. Check the price first with [Estimate a batch](/api-reference/batches/estimate). It checks every input and says what the list would cost and how many inputs your balance covers. Nothing runs and nothing is charged.
2. Start it with [Start a batch](/api-reference/batches/start), with the same body.
3. Follow it with [Get a batch](/api-reference/batches/get), then read the rows with [Get a batch's rows](/api-reference/batches/get-rows) or [as CSV](/api-reference/batches/get-rows-csv). Each row says which input it came from.

```bash
curl -X POST https://api.valendata.com/v1/skills/austin-dentists/batches \
  -H "Authorization: Bearer $VALENDATA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"inputs": [{"city": "Dallas"}, {"city": "Houston"}, {"city": "El Paso"}], "max_results_per_input": 20}'
# → 202 {"batch_id": "bat_4f2a9c1e7b3d", "status": "queued", "total": 3, "poll_url": "/v1/batches/bat_4f2a9c1e7b3d", ...}
```

What to know:

- **Each input is an ordinary run**, charged like one. A list costs the sum of its runs.
- **Every input is checked before anything starts.** One bad input refuses the whole list with a `422` that names each problem by its position.
- **Limits**: 1 to 10,000 inputs per list, up to 500 rows per input, and up to 5 of your lists running at once. Inputs run a few at a time, by default half of what your account may run at once for the skill, so your other runs are not kept waiting.
- **Credits**: a list your balance covers less than half of is refused with `402`. Send `allow_partial: true` to run as many inputs as your credits allow. When the credits run out, the rest are not started.
- **Stopping**: [Cancel a batch](/api-reference/batches/cancel) stops it. Rows already found are kept, and runs that ran stay charged.

From an AI assistant, the tools are `run_skill_batch` and `get_batch`. See [MCP tools](/ai-assistants/mcp-tools).

### Run settings

These go next to the inputs and are not inputs themselves:

| Setting | What it does |
| --- | --- |
| `max_results` | Rows to return, 0–500. `0` returns the whole list. Leave it out to use the skill's saved default. |
| `max_pages` | Page limit for skills that page through results. `0` means all pages. |
| `version` | Run one [version](/concepts/keeping-skills-working#versions) for this call only. |
| `browser_type` | `remote` (cloud browser), `extension` (your own browser), `local_profile`, or `none`. |
| `profile_id` | The [browser profile](/concepts/logins-and-browser-profiles) to use. |
| `proxy_config` | Region: a country code, `random`, or `none`. |
| `max_age` | Seconds. Accept an earlier answer with the same inputs, for a share of the price. See [Cached answers](/api-reference/runs/run-skill#cached-answers). |

Inputs are checked before anything runs. A missing input, a wrong type, or an unknown name returns `422` with every problem listed, and nothing is charged. See [Errors and limits](/api-reference/errors).

## Values an input takes

Some inputs only take values the site has, like a category or a budget filter. A skill learns these values from the site's own links and from earlier runs. Each input in [`GET /v1/skills/{slug}`](/api-reference/skills/get) lists them:

| Field | What it is |
| --- | --- |
| `parameters[].known_values` | Values the site is known to accept for this input, including the one it was recorded with. Empty when the skill has not learned any yet. |
| `parameters[].refused_values` | Values the site was asked to take once and would not. |

Only the skill's owner and its workspace see them, because they include values other people ran. On someone else's public skill, both lists are empty.

When you send a new value:

- **A value the site keeps as its own code** is learned the first time. The site may store "Under $50,000" as a number in its address, for example. The run answers at once that the value is being learned, and returns no rows for the recorded value in its place. Run the skill again in a few minutes, and it uses the new value.
- **A value the site will not take** is refused with the reason and the closest known values. Pick one of those and run again.
- **A value the site's API has no rows for**: on a skill built on an [open API](/guides/create-a-skill#open-apis-first), the run fails with an `error` like `The site's API (api.example.com/jobs) has no rows for category='robotics'. That may not be a value it has — the skill's input_schema lists the values it is known to take.` Its `failure_class` is `user`: the value is the problem, not the skill. The input's `examples` in `input_schema` list the values it is known to take. In the app the run shows **Nothing found for "robotics"** and those values.

An input that acts as a filter takes a value in the filter's own form: text for `contains`, `equals`, and `one_of` (comma-separated), a number for `min` and `max`, and a date or a span like `7d` for `since`. See [Inputs](/concepts/skills#inputs).

## From an AI assistant

Each skill is a tool named `skill_<slug>`. See [Connect your AI assistant](/ai-assistants/connect).

## What comes back

The rows, plus fields that say how far to trust them, which version ran, and what it cost. See [Runs](/concepts/runs).
