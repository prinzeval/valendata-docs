There are three ways to get a skill:

| Way | Best for | Can sign in to sites? |
| --- | --- | --- |
| [From a sentence](#from-a-sentence) | Public pages: search results, listings, directories. | No |
| [By recording it](#by-recording-it) | Tasks behind your sign-in, or that need exact clicks. | Yes |
| [From the marketplace](/guides/use-the-marketplace) | Common tasks someone has already built. | Depends on the skill |

## From a sentence

You describe the task and the page it starts on. Valendata first looks for the site's [open API](#open-apis-first). If none fits, it does the task in a browser, learns the steps, and checks them with one more run. This takes a few minutes.

You can start it from:

- **The app**: **My Skills → Create Skill → Describe it**. The product tour and Igris, the in-app assistant, can do it too.
- **Your AI assistant**: ask it to create a skill. It uses the `create_skill` tool. See [MCP tools](/ai-assistants/mcp-tools).
- **The API**: [`POST /v1/skills`](/api-reference/skills/create).

Optionally name the **inputs** (with the example value the task uses) and the **output fields** you want. If you leave them out, Valendata works them out from the task. Names are turned into `snake_case`, so `Phone number` becomes `phone_number`.

### Open APIs first

Many sites publish their data through an open API: a web address that answers with data, without a browser. Before it opens a browser, Valendata looks for one, then checks that the answer holds the fields you asked for. No cookie of yours is sent. While it looks, `progress` reads like `Looking for an open API for bayse.markets…`, then `Found its public API — building the skill on it` and `Checking the API returns the fields…`.

**When the site blocks our server.** If you have agreed that Valendata may use your Chrome and the Valendata extension is connected, Valendata may open the start page once in a background tab of your Chrome to finish the search, then closes the tab. Your other tabs are not touched, and nothing is recorded. `progress` says `The site blocked our server — reading its page in your Chrome…`.

**Inputs the task names.** When the task names a value, such as "jobs in the programming category", and the API takes no parameter for it, Valendata maps the input another way the source allows: a part of the address (the category's own feed, a store's collection) or a filter on an output field. A part of the address must be one of the site's own values, and a filter must keep some of the sample rows. See [Inputs](/concepts/skills#inputs).

If an API checks out, the skill is built on it. There is no recording. Each run calls the API directly, with no browser, and returns the site's own values: one call per page of results, plus one per row for a [list plus detail](#list-plus-detail) skill. The creation's `source` is `api`, and `api_endpoint` names what it reads, such as `gamma-api.polymarket.com/markets`. In the app, the skill shows **Reads gamma-api.polymarket.com's public API**.

If none checks out, it records in a browser as usual. `progress` says `No open API to build on — recording it in a browser`, `source` is `browser`, and `source_note` says what the search found.

Two optional fields change this:

| Field | What it does |
| --- | --- |
| `source` | `auto` (default): an open API first, then a browser. `api`: an open API only. When none is found, the creation fails, and the credits it used are not given back. `browser`: skip the search and record in a browser. |
| `api_url` | The API's address when you already know it, such as `https://api.example.com/v1/items?status=open`. Valendata skips the search, matches the answer to your fields, and checks it. It must answer without a key. In the app, open **Have an API link?** |

A creation with a saved login (`login_id`) does not look for an API: its data is behind a sign-in. Sending `login_id` with `source: "api"`, or `api_url` with `source: "browser"`, is refused.

#### List plus detail

Some APIs list their records without every field. A jobs list can leave out each job's description, and a markets list each market's full rules. When a list checks out but leaves fields you asked for empty, Valendata looks for the API's call for one record. It tries the record's own link to itself, then the usual address for one record (such as `…/jobs/{id}` or `…/products/{handle}.json`), then the API docs it read. It calls each one for two or three real rows and keeps it only when every answer is about that row. It then reads your fields from the answer and checks the whole skill again. `progress` says `The list lacks description — looking for the API's call for one record…`.

A skill built this way makes one more call per row it returns, so `max_results` limits those calls too. At most four go out at once, and each waits its turn with the site like any other call. If one row's call fails, that row's fields from it are empty and the run still succeeds. The run's `drifted_fields` says how many rows were left empty and why. There is no charge per call: a run costs what any run of an API skill costs.

[`GET /v1/skills/{slug}`](/api-reference/skills/get) names the second call in `fast_path_detail_endpoint`. In the app, the skill's **Optimizer** tab shows it under **Then, for each row**, with the fields read from it. To add such a field to a skill you already have, use [Add fields](/guides/improve-a-skill#skills-built-on-an-open-api).

### Which browser records it

The browser is used only when no open API is found. Pick it under **Browser** in the app, or send `browser` in the API and to `create_skill`:

| `browser` | In the app | Where it records |
| --- | --- | --- |
| `auto` (default) | **Automatic** | A Valendata cloud browser. It switches to your Chrome when the cloud is busy or the site blocks cloud browsers. |
| `cloud` | **Cloud** | A Valendata cloud browser only. |
| `extension` | **My Chrome** | Your own Chrome, through the Valendata extension. Chrome must be open with the extension connected. |

Pick **My Chrome** for sites that block cloud browsers. When **Automatic** switches for that reason, `progress` says `The site blocked the cloud browser — recording on your Chrome instead`. A creation with a saved login (`login_id`) always records on the cloud. For how the two browsers differ when a skill runs, see [Where a skill runs](/concepts/skills#where-a-skill-runs).

<CodeGroup>

```bash curl
curl -X POST https://api.valendata.com/v1/skills \
  -H "Authorization: Bearer $VALENDATA_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: dentists-austin-001" \
  -d '{
    "task": "Search for dentists in Austin and list them",
    "start_url": "https://www.google.com/maps",
    "inputs": {"city": "Austin"},
    "output_fields": {"name": "business name", "rating": "star rating", "phone": "phone number"}
  }'
```

```python Python
import os, time, requests

API = "https://api.valendata.com"
HEADERS = {"Authorization": f"Bearer {os.environ['VALENDATA_API_KEY']}"}

creation = requests.post(
    f"{API}/v1/skills",
    headers={**HEADERS, "Idempotency-Key": "dentists-austin-001"},
    json={
        "task": "Search for dentists in Austin and list them",
        "start_url": "https://www.google.com/maps",
        "inputs": {"city": "Austin"},
        "output_fields": {"name": "business name", "rating": "star rating", "phone": "phone number"},
    },
).json()

while creation["status"] not in ("ready", "needs_fix", "failed", "cancelled"):
    time.sleep(30)
    creation = requests.get(f"{API}{creation['status_url']}", headers=HEADERS).json()
    print(creation.get("progress"))

print(creation["status"], creation.get("slug"), creation.get("next_step"))
```

</CodeGroup>

The call answers at once with a `creation_id`. Read [`GET /v1/skill-creations/{creation_id}`](/api-reference/skills/get-creation) about every 30 seconds. Stop when `status` is `ready`, `needs_fix`, `failed`, or `cancelled`.

| `status` | Meaning |
| --- | --- |
| `queued` | Waiting to start, or looking for an open API. While it waits for a free browser, `queue_position` says how many of your creations are ahead. |
| `recording` | The browser is doing the task. |
| `validating` | Saved as a skill (`slug` is set). Valendata runs it once more to check it. |
| `ready` | Passed the check. You can run it. |
| `needs_fix` | Saved as a **draft** skill (`slug` is set), but the check run did not pass. Fix it with [`POST /v1/skills/{slug}/improve`](/api-reference/improvements/improve) (MCP: `improve_skill`). Do not create it again. |
| `failed` | Did not work and nothing was saved. `error` says why and `diagnosis` suggests what to try. The credits it used are not given back. |
| `cancelled` | You [stopped it](/api-reference/skills/cancel-creation) while it was building. Nothing was saved. |

Each check also tells you:

| Field | What it is |
| --- | --- |
| `task`, `start_url`, `name` | What you asked for. |
| `progress` | The latest step in plain words, such as `Step 4: typing 'trouser' into the search box`. While it waits, it reads like `Waiting for a free browser — 1 ahead`. Show it to whoever is waiting. |
| `browser` | Where it records: `cloud` or `extension` (your Chrome). `null` until it starts, and for a skill built on an API. |
| `source` | How the saved skill reads the site: `api` (its open API) or `browser` (a recording). `null` until a skill is saved. |
| `api_endpoint` | For `source: "api"`, the API it reads, as host and path. Otherwise `null`. |
| `source_note` | For `source: "browser"`, why it was not built on an open API. |
| `queue_position` | While it waits for a free browser, how many of your creations are ahead of it. Otherwise `null`. |
| `next_step` | One sentence that says what to do next. |
| `sample_rows` | Up to 3 rows from the recording, set for `needs_fix` and `ready`. `sample_row_count` is how many rows the recording got. |
| `credits_charged` | Credits used so far, to 0.01. |

A creation that needs a fix looks like this:

To see all your creations, newest first, use [List skill creations](/api-reference/skills/list-creations). Pass `status=active` for the ones still going.

To stop one that is still going, use [Cancel a skill creation](/api-reference/skills/cancel-creation). It stops at its next step. Credits it already used are not refunded.

**Limits:** up to 10 creations at a time, counting the ones waiting, at least 10 credits to start, and 30 minutes per creation. Creations that cannot start yet wait in a queue (`queued`) for a free browser. Nothing is charged while one waits.

**Behind a sign-in:** if the start page asks you to sign in, pick a saved login under **Sign in with** (`login_id` in the API, from [List logins](/api-reference/logins/list)). A cloud browser signs in with it first, and the new skill keeps using that login. Without one, the creation stops and asks you to save a login for the site, then create it again.

## By recording it

<Steps>
  <Step title="Start recording">
    Open a new session from the dashboard. In the chat box, switch on **Record Skill**. It shows **Recording...** while it is on.
  </Step>
  <Step title="Do the task">
    Type the task for the agent, or use the browser yourself: sign in, search, page through results, and reach the data you want. Every step is recorded.
  </Step>
  <Step title="Stop and publish">
    Stop the session. The recording is saved under **Configs**. Open it, click **Publish as skill**, give it a name and description, choose the visibility, and click **Publish Skill**.
  </Step>
  <Step title="Check the inputs and output fields">
    Open the skill. Under **Available inputs**, turn on the ones a run should be able to change. Under **Data contract**, click **Suggest** to detect output fields from the recording, then rename them or [change their type](/concepts/skills#output-field-types).
  </Step>
</Steps>

If the site needs a sign-in on later runs, attach a browser profile or a saved login. See [Use a saved login](/guides/use-a-saved-login).
